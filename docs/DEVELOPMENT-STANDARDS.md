# 开发标准与迭代准则

> 本文件不是通用最佳实践的搬运，而是**本项目 38 次提交里真实付出过代价的教训**的固化。
> 每条标准都标注了它来自哪一次真实事故——没有出处的条目不进本文件。
>
> 适用对象：本工程（及后续同类）的开发者与 AI 助手。
> 配套文档：功能清单 `FEATURES.md`、HTTP 契约 `api-contract.md`、实施计划 `PLAN.md`。

---

## 一、验证纪律（最高优先级）

### 1.1 完成 = 有证据，不是"我改了"

**标准**：任何交付前必须给出**可复现的验证输出**，不接受"应该没问题""逻辑上是对的"。

**来源**：多轮返工。本项目反复出现的模式是——代码写完、编译通过、`pytest` 全绿，但真机一跑就错：

| 案例 | 表面状态 | 实际 |
|---|---|---|
| 自包含 agent 替换外部 agent | 门禁 6/6 全绿 | 丢掉了 `FILE_PUSH/FILE_PULL` 传输协议，拉取/上传全断 |
| 引擎设备数显示 0 | 接口 200，列表正常 | 计数口径与实时探测不同口径，用户一眼看穿 |
| 迁移给 nullable 列填 0 | 迁移执行成功 | 0 被当成"已采集值"，惰性回填永久卡死 |

**做法**：门禁只是**下限**，不是结论。真机链路（发现→浏览→传输→改写→删除）必须端到端跑一遍。

### 1.2 攻击者视角验证安全修复

**标准**：安全类修复的验收标准是**攻击复测**，不是代码审阅。

**来源**：`shlex.quote` 保护的是执行命令那台机器的 shell，而 `adb shell` 会在**设备上重新解析**——引号早已被剥掉。实测：

```
POST /files/mkdir {"path": "/sdcard/Download/x$(touch /sdcard/Download/PWNED)"}
→ 200 "目录已创建"        # 设备上真的出现了 PWNED 文件
```

修复后必须重打同一发：6 种 payload（`$()`、`;`、`` ` ``、`|`、`&`、引号）全部 400 且设备无残留，才算完成。

### 1.3 复现最坏用户操作，而不是 happy path

**标准**：验证场景要取**用户最可能做的蠢操作**，不是最理想的路径。

**来源**：root 开关报 400。单个 root/unroot 一切正常，**背靠背连点**（root→unroot→root 无间隔）必炸——`adb root` 让 adbd 重启、设备离线数秒，落在这个窗口的操作直接失败。

修完用「背靠背 5 连击」验收：5 次全部 200 才算通过。

### 1.4 失败分支必须被测试覆盖

**标准**：happy path 通过 ≠ 功能正确。**每个错误分支都要有测试**。

**来源**：`_wait_until_online` 里用了 `asyncio.sleep` 但 `base.py` **没有 `import asyncio`**——设备恢复快时永远走不到那行，功能"看起来正常"；一旦设备持续离线就 `NameError` → 500。

### 1.5 指标要看趋势，不看绝对值

**标准**：CPU 百分比这类**需要两次采样做差**的指标，首次必然是 `None`。看到 `None` 先确认语义（无基线）再判定 bug——本项目两次把"首次无基线"误判成"采集中断"。

## 二、改动边界

### 2.1 替换组件 = 替换全部契约

**标准**：换掉一个组件，等于换掉它**全部隐式契约**。先列清单再动手。

**来源**：把外部 `device_server` 换成自研 agent 时，只对齐了「裸 adb 命令」这一条，漏了文件传输协议。验收清单应当是：

```
□ 设备发现   adb devices -l
□ shell      adb -s X shell ...
□ 文件拉取   FILE_PULL 协议 + md5
□ 文件推送   FILE_PUSH 协议 + md5
□ 认证       AUTH 握手
□ root 切换  adbd 重启后的等待
```

### 2.2 改不变量要枚举所有消费方

**标准**：改动一个全局不变量（如"设备 UID 与接入方式解耦"）时，必须枚举**所有读取该不变量的展示与统计**，逐个复核口径。

**来源**：UID 解耦后，设备行归属变成"最后同步者赢"的零和游戏 → 引擎表的设备数按归属统计就失真了。**修完设备列表 ≠ 修完所有依赖它的统计**。

### 2.3 扩展点优先于新分支

**标准**：新增一种能力形态（如第三种远程接入方式），优先实现抽象基类的最小接口，**其余能力从基类继承**，而不是复制粘贴一份新实现。

**来源**：`Transport` 基类把 agent 的能力收敛到 `shell()` 一个原语。增加 SSH 直连时**只重写了 8 个抽象方法**，指标/root/路径白名单/设备属性等十余项能力全部零成本继承。

**判据**：新实现的代码量应当远小于"从零做一遍"。

### 2.4 补丁脚本要幂等，且幂等判据要强

**标准**：patch 脚本必须可重复执行，**判据要用新内容里的关键行**，不能用"任意相关字符串"。

**来源**：用「文件里出现 `SshAdbTransport` 就认为已导入」做幂等判断 → 文件里**引用**了但**没导入**，脚本跳过，运行时 `NameError`。正确判据是「新内容的关键行已存在」。

### 2.5 锚点会漂移，行号不会

**标准**：多轮修改过的文件，patch 一律**先读实际内容再改**；优先按行号/结构插入，避免长字符串锚点。

**来源**：README 被 patch 过多次，字符串锚点连续失败 4 次（含三级标题写成二级、缩进不同、措辞被别的会话改过）。改用「先 `grep -n` 看真实行，再按行操作」一次成功。

## 三、编码约定

### 3.1 命令类输入一律走白名单，不靠转义

**标准**：任何进入 shell 的用户可控内容，先做**字符白名单校验**，再谈引号。

**来源**：`shlex.quote` 对 `adb shell` 无效（设备端重新解析）。正确做法：`assert_safe_device_path()` 拒绝 `; | & $ \` < > ( ) ' " * ? [ ] { }` 等元字符，**平台侧与 agent 侧各有一份**。

### 3.2 静态属性走"采集一次 + 惰性缓存 + 惰性回填"

**标准**：不变的数据（核心数、ABI、Android 版本）不要放进轮询循环：

```
采集 → 传输层按设备缓存 → 路由发现字段为空才回填 → 落库
```

**收益**：轮询开销为零；`Transport` 基类实现一次，三种通道共享。

### 3.3 不可信的返回值要按文本判定，不信退出码

**标准**：当命令的退出码天生不可靠时（`adb root` 因为重启 adbd **必然**返回非 0），以**输出文本**为准，并在注释里写明原因。

**来源**：`adb root` 成功时退出码非 0，早期实现把它当失败 → 用户永远看不到"已以 root 模式重启"。

### 3.4 幂等操作返回成功

**标准**：目标状态已达成时，返回**成功**而非错误。

**来源**：`adb unroot` 在未 root 的设备上输出 `adbd not running as root`，这不是失败——请求已被满足。早期把它判成错误 → 批量取消 root 出现"0/1 台成功"。

### 3.5 瞬态错误要等待 + 重试，不要直接甩给用户

**标准**：设备重启类的**瞬态窗口**由服务端吸收：先等设备在线 → 失败自动重试一次 → 仍失败才报错。

**来源**：root 开关的 400 报错（见 1.3）。修完连点 5 次全部 200。

### 3.6 迁移对 nullable 列必须用 NULL

**标准**：新增 nullable 列时，迁移脚本填 `NULL`，**不要填列默认值 0**——0 会被当成真实值，永久阻塞惰性回填。

### 3.7 显示口径必须同源

**标准**：同一个概念在表格与弹窗里必须是**同一个数据源**，不允许"表格按 A 口径、弹窗按 B 口径"。

**来源**：引擎设备数（表格：按设备行归属统计）vs 探测台数（弹窗：实时探测）→ 同屏两个数字打架。改为引擎表存**最近一次探测的真实值**，两处同源。

### 3.8 UI 沿用既有视觉语言，不自创样式

**标准**：新页面/新列**照抄**已有页面的模式（双行名称、语义色标签、等宽地址、省略+气泡），不发明新样式。

**来源**：设备页先立了视觉模式，后续机器页、设置页全部照搬——用户学一次就会用全站。

## 四、协作与流程

### 4.1 每个需求都要有验收信号

**标准**：动手前先写清楚「怎样算做完」，最好是**可执行的命令**（真机操作、断言、DOM 文本）。

**来源**：「拉取功能没有实现」「点击 root 报 400」这类反馈，都源于验收信号缺失——以为做完，其实链路只通了一半。

### 4.2 改 schema 的同轮内，验证顺序固定

```
① 重启让迁移落地  →  ② 写数据  →  ③ 重启让应用加载  →  ④ 端到端验证
```

**来源**：迁移未执行时 `UPDATE` **静默失败**，还误以为是"平台侧没传 token"，多绕了一轮。

### 4.3 外部工具的配置改动：先看再写 + 先备份

**标准**：改用户工具（cc-switch、CI、IDE 配置）时：① 先读现有结构**照抄字段名**；② 写前备份；③ 写后读回验证 + 完整性检查；④ **不把任何凭据完整打印到输出**。

### 4.4 文档随交付更新

**标准**：功能清单（`FEATURES.md`）的勾选状态**必须与真实验证对齐**，不能凭印象打勾；新增能力同步补文档条目。

### 4.5 一次性脚本要归档到统一目录

**标准**：写错位置的一次性脚本，用完**挪到 `scripts/patches/legacy/`** 保留演进痕迹，不要散落在包目录里。

## 五、迭代节奏（可复用的工作循环）

```
1. 取证      先量现状，不凭印象（跑一遍、读源码、查 git 历史）
2. 诊断      一行说清「问题是什么 + 证据在哪 + 下一步做什么」
3. 实施      改前备份，改后立刻编译/测试
4. 真机验证  端到端跑链路，含最坏操作序列
5. 回归      跑门禁（6 步）+ 确认服务无副作用
6. 沉淀      更新清单/文档 → 提交 → 推送
```

**迭代期的固定动作**（每轮都做，不省）：

| 频率 | 动作 |
|---|---|
| 每轮 | 跑 `scripts/verify.sh`（6 步门禁） |
| 每轮 | 真机跑一遍受影响的主链路 |
| 每轮 | 更新 `docs/FEATURES.md` 勾选状态 |
| 每轮 | 提交信息写清「根因 → 修法 → 证据」 |
| 每日 | 更新 `docs/api-contract.md` 与界面功能清单 |
| 里程碑 | 归档 patch 脚本，更新 `PLAN.md` |

## 六、工具使用约定

| 场景 | 约定 |
|---|---|
| 改大文件 | 用 patch 脚本（可重跑、可审计），不用 `sed -i` 盲改 |
| 调试 500 | 让 traceback **完整暴露**（直接调函数），别在中间件帧里找 |
| 探索性命令 | 先读文件确认符号存在，再写命令（省掉"想当然"的往返） |
| 凭据 | 不在输出里打印完整 key；验证用前缀 + 长度 |
| 远程改动 | 幂等追加（`grep -qF ... || echo ... >>`），可重复执行 |

## 七、检查清单（提交前逐项打勾）

**代码**
- [ ] 改动的影响面已枚举（不变量、统计口径、所有消费方）
- [ ] 新入口有对应测试；错误分支也有测试
- [ ] 用户可控输入经过白名单校验
- [ ] 编译/类型检查通过

**验证**
- [ ] 门禁 6 步全绿
- [ ] **真机端到端**跑过受影响链路
- [ ] 最坏操作序列（连点/并发/异常输入）验证过
- [ ] 服务无副作用（health、其它页面仍正常）

**文档与提交**
- [ ] `FEATURES.md` 勾选状态与验证一致
- [ ] 契约/说明文档同步
- [ ] 提交信息含根因与证据
- [ ] 已推送远端

## 附：本标准的新增方式

本文件**只增不删**，每新增一条必须满足：

1. 有**真实出处**（某次提交 / 某个 bug / 某次返工）；
2. 写清「**标准是什么**」+「**为什么**（来源案例）+「**怎么做**」；
3. 可被下一个人（或下一轮 AI）**直接执行**——不能是"要重视质量"这类口号。

发现标准与实践冲突时：**先按标准执行，再更新标准**——不要让文档悄悄落后于现实。
