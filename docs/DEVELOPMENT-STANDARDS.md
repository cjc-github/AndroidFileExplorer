# 开发规范

> 通用开发规范，与技术栈、语言、框架无关，适用于任何项目的日常开发与 AI 协作。
>
> 原则：**每条规则都要能被"照着做"，而不是"理解了道理"。**
> 因此本文以「可执行的判定条件 + 反例」为主，不写口号。

---

## 一、交付与验证

### 1.1 完成 = 有证据

**规则**：声称完成时，必须同时给出**可复现的验证输出**（命令及其输出、截图、可查询的记录）。

**判定**：能被第三方按你给的命令重跑并得到同样结果。

```
✗ 「应该没问题，逻辑上是对的」
✗ 「代码写完了」（无输出）
✓ 「测试 42 项通过；端到端执行 X 后，存储中 Y=Z」
```

### 1.2 自动化门禁是下限，不是结论

**规则**：CI/测试通过只代表**已覆盖的部分**没问题。影响用户的主链路必须**端到端手工跑过一次**。

**判定**：能否说出"用户从哪进去、点什么、看到什么"这三步。

### 1.3 复现最坏操作，而非理想路径

**规则**：验证场景取**用户最可能做的蠢操作**：连点、并发、重复提交、空输入、超长输入、异常中断。

**判定**：至少覆盖「双击」「中途切换」「超时」三种。

```
✗ 只验证「点一次按钮，结果正确」
✓ 验证「连点 5 次，全部返回成功且状态一致」
```

### 1.4 错误分支必须有测试

**规则**：happy path 通过 ≠ 功能正确。**每个错误分支、边界条件都要有测试**。

**反例**：某函数用了 `asyncio.sleep` 却漏了 `import asyncio`——正常路径永远走不到那行，功能"看起来正常"，只在异常路径崩溃。

**判定**：能否列出「输入 → 期望输出」的对照表，且每行都有对应测试。

### 1.5 区分"首次无数据"与"采集失败"

**规则**：需要多次采样做差值、或依赖历史基线的指标，**首次必然为空**。看到空值先确认语义，再判定为缺陷。

### 1.6 修缺陷时先复现，再修

**规则**：动手前先构造出**稳定复现**（命令/步骤），并保留它作为回归测试。

**判定**：修复后，同一条复现路径必须从"失败"变成"通过"。

## 二、改动边界

### 2.1 替换组件 = 替换它的全部契约

**规则**：替换/重写一个实现时，先列出旧组件的**全部对外行为**（含隐式的：协议、字段、副作用、错误语义），逐条对齐。

**判定**：是否存在"旧组件能做、新组件做不了"的行为。

```
替换前先列清单：
□ 正常路径
□ 边界/异常路径
□ 协议与数据格式
□ 副作用（写文件/发消息/改状态）
□ 错误语义（错误码、异常类型）
```

### 2.2 改全局不变量，要枚举所有消费方

**规则**：修改影响多个模块的基础规则（唯一标识、命名、归属、时间语义）时，**枚举所有读取它的展示与统计**，逐个复核口径。

**判定**：能否列出「哪些地方读了这个值 → 各自的口径是否仍成立」。

**反例**：唯一标识改为与来源无关后，列表正确了，但"按来源统计数量"的报表失真了——归属变成"最后写入者赢"。

### 2.3 扩展优先于复制

**规则**：新增一种实现/形态时，优先实现**抽象接口的最小集合**，其余能力从基类继承。

**判定**：新实现的代码量是否**显著小于**"从零做一遍"。

### 2.4 保持单一事实来源

**规则**：同一概念在界面上只允许有一个口径来源。表格与弹窗、列表与详情、日志与指标必须一致。

**判定**：随机抽查两处展示同一概念，数值是否必然相等。

### 2.5 改动范围外的行为要复查

**规则**：改动 A 时，检查是否**意外影响**了依赖 A 的其它路径（不只是调用了 A 的地方，还有**读同一份数据**的地方）。

## 三、编码规范

### 3.1 不可信输入一律校验，不靠转义

**规则**：任何来自用户/外部/文件的内容，进入命令、SQL、路径、模板前，先做**白名单或类型校验**。

**判定**：能否说出"这段输入非法时会发生什么"。

**反例**：转义对当前 shell 有效，但对会**二次解析**的下游（如把命令转发给另一台机器/另一个进程再执行一次）无效——转义用在了错误的一层。

### 3.2 静态数据不要放进轮询/热路径

**规则**：不变的数据（硬件信息、配置、版本）采集一次并缓存，按需惰性回填并持久化。

**判定**：轮询循环里有没有查询不变数据。

### 3.3 退出码不可信时，以输出内容为准

**规则**：当命令的退出码天生不可靠时（会重启服务、返回非 0 但成功），**以输出文本判定**，并在代码注释里写明原因。

### 3.4 幂等操作返回成功

**规则**：目标状态已达成时，返回**成功**而非错误。

```
✗ 「设备本就没开的功能，执行关闭」→ 报错
✓ → 成功，附带「本来就处于目标状态」
```

### 3.5 瞬态错误要等待 + 重试

**规则**：服务重启、连接池刷新等**短暂不可用窗口**由服务端吸收：先等待就绪 → 自动重试一次 → 仍失败才对外报错。

**判定**：连续快速触发同一操作，是否全部成功。

### 3.6 错误信息对用户可读

**规则**：错误信息要说清**发生了什么、为什么、怎么办**。内部异常对用户展示为可理解的说明，对日志保留原始细节。

### 3.7 数据变更用 NULL 表达"未知"

**规则**：nullable 字段的初始值用 `NULL`，不要用 `0`/`""` 等**有含义的值**——否则"未采集"会被误读成"采集到了 0"，且永久阻塞后续回填。

### 3.8 命名与结构表达意图

**规则**：函数名说明"做什么"，注释说明"为什么这么写"（尤其是反直觉的写法与绕过方案）。

## 四、变更流程

### 4.1 动手前先定验收信号

**规则**：每个需求先写清「怎样算做完」，最好是**可执行的命令或断言**。

```
「优化加载速度」          → 不合格
「列表接口 P95 < 200ms」 → 合格
```

### 4.2 涉及数据结构的改动，验证顺序固定

```
① 应用变更让结构生效 → ② 写入数据 → ③ 重启让程序读取 → ④ 端到端验证
```

**反例**：结构变更尚未生效时执行写入命令会**静默失败**，容易被误判为"程序没读"。

### 4.3 改第三方工具/配置：先看再写 + 先备份

**规则**：修改用户已有工具的配置（IDE、CI、CLI、GUI 应用）时：
① 先读现有结构**照抄字段名与格式**；
② 写前备份；
③ 写后读回验证 + 完整性检查；
④ 不把凭据完整打印到输出。

### 4.4 一次性脚本统一归档

**规则**：写错位置、用完即弃的脚本，挪到统一的 `scripts/legacy/` 目录保留，不散落在业务包目录里。

### 4.5 文档随交付更新

**规则**：功能清单/使用说明的勾选状态必须与**真实验证**对齐，不能凭印象打勾。

## 五、脚本与自动化

### 5.1 脚本必须幂等，且判据要强

**规则**：脚本可重复执行；判断"是否已应用"要用**新内容里的关键行**，不能用"任意相关字符串"。

**反例**：用「文件里出现了 `Foo` 就认为已导入」判断——文件里可能只是**引用**了 `Foo` 而没有导入。

### 5.2 修改多处文件用脚本，不用逐条手改

**规则**：涉及多处的机械改动写成**可重跑、可审计**的脚本；避免不可追溯的正则/就地编辑。

### 5.3 长文本锚点会漂移，结构定位更稳

**规则**：多轮修改过的文件，先读实际内容再定位；优先按行号或结构特征操作，避免依赖长字符串锚点。

### 5.4 脚本失败要显式暴露

**规则**：脚本里的断言/校验失败必须**非零退出**并打印原因，不允许静默跳过。

**反例**：`assert old in source` 失败后异常被吞，脚本"成功"退出但什么都没改——这种假成功比失败更危险。

## 六、界面与交互

### 6.1 沿用既有视觉语言

**规则**：新增界面**照抄**已有页面的模式（间距、标签、色彩语义、表格结构），不发明新样式。

**判定**：新页面能否让人"不看说明就懂"。

### 6.2 语义色只表达状态，不表达装饰

**规则**：同一状态在任何页面用同一颜色（如"成功=绿、异常=红"）。

### 6.3 破坏性操作必须二次确认

**规则**：删除、清空、覆盖等不可逆操作需确认；确认文案要说清**影响范围**。

### 6.4 等待态与失败态要区分

**规则**：「加载中」「无数据」「加载失败」是三种不同状态，界面要能区分。

### 6.5 数值列给视觉层次

**规则**：关键数值（数量、占比、耗时）用字重/颜色区分主次；辅助信息用次级样式，不要全部同等强调。

## 七、协作与 AI 协作

### 7.1 任务描述要包含验收信号

**规则**：给 AI 或人的任务里写明「怎样算完成」，避免"做完了但没做对"。

### 7.2 AI 产出必须复核

**规则**：AI 给出的代码/结论要**独立复核**，尤其涉及安全、并发、数据一致性时——不要因为"测试通过"就停止怀疑。

### 7.3 上下文交接要写清状态

**规则**：跨会话/跨人交接时，写明：目标、验收标准、已验证、已排除、失败次数与当前状态。

### 7.4 不确定就停下问

**规则**：缺少私有信息、需求有多种实质不同的解读、或需要新增授权时，**问一个关键问题**并继续推进不受影响的部分。

---

## 八、提交与记录

### 8.1 提交信息写"为什么"

**规则**：提交信息包含根因与修法；有验证证据时附上关键结果。

```
✗ fix bug
✓ fix(core): 用户路径未做白名单校验导致命令注入
    下游会二次解析，转义无效；改为白名单校验
```

### 8.2 提交前检查清单

- [ ] 编译/类型检查通过
- [ ] 自动化测试通过，且**新增测试覆盖本次改动**
- [ ] 影响面已枚举（消费方、口径、副作用）
- [ ] 端到端链路手工验证过
- [ ] 最坏操作序列验证过
- [ ] 文档/清单同步
- [ ] 工作树无遗留调试代码、临时文件

### 8.3 不提交生成物与本地状态

**规则**：依赖目录、构建产物、运行时数据、密钥、IDE 配置一律不入库。

**判定**：`git status` 里是否有本该忽略的东西。

## 九、迭代节奏

### 单个变更的闭环

```
1. 取证      先量现状（跑一遍 / 读代码 / 查历史），不凭印象
2. 诊断      一句话：问题是什么 + 证据在哪 + 下一步做什么
3. 实施      改前备份；改完立即编译/测试
4. 验证      端到端 + 最坏操作 + 回归
5. 沉淀      更新文档 → 提交 → 推送
```

### 固定节奏

| 频率 | 动作 |
|---|---|
| 每次变更 | 跑自动化门禁 + 受影响链路的端到端验证 |
| 每次变更 | 更新受影响文档/清单的勾选状态 |
| 每日 | 同步接口契约与界面功能说明 |
| 里程碑 | 归档临时脚本、清理技术债、回顾"哪些坑可以变成规则" |

## 十、常见反模式速查

| 反模式 | 正确做法 |
|---|---|
| 转义代替校验 | 白名单校验下游真正解析的那一层 |
| 靠退出码判断成功 | 输出不可靠时看内容，并注释原因 |
| 首次读不到值就当 bug | 先确认是不是"无基线/未采集" |
| 只测正常路径 | 错误分支、边界条件同样要测 |
| 修完就交付 | 复现路径必须从失败变通过 |
| 改了 A 就以为完事 | 枚举所有读 A 的消费方 |
| 复制一份新实现 | 抽最小接口，其余继承 |
| 表格与弹窗各算各的 | 单一事实来源 |
| 脚本静默失败 | 断言失败即非零退出并说明原因 |
| 长字符串锚点改文件 | 先读实际内容，按行/结构定位 |
| 手改多处文件 | 写可重跑脚本 |
| 首次迁移后立刻写数据 | 确认结构已生效再写 |
| 凭据打印到输出 | 只展示前缀与长度 |
| 用 `0` 表示"未采集" | 用 `NULL` |

## 附：如何使用这份规范

- **写代码时**：对照第三、五章的规则，提交前过 8.2 的清单。
- **Code Review 时**：用「判定」列提问——「你如何确认影响面已枚举？」
- **引入 AI 协作时**：把第一章（验证纪律）与 7.1（任务要带验收信号）作为最优先约束。
- **迭代沉淀时**：每季度回顾一次，把新踩的坑按本文格式补进来（规则 + 判定 + 反例）。
